# みゅけ システム理念書 — 他AI向け

『みゅけ、きょうも開発中』のシステム設計の理念を、実装・提案・レビューに
関わるAI向けに成文化したもの。個別仕様（数値表・UI仕様）より上位の文書であり、
判断に迷う場面では本書が一般的な放置ゲーム/クリッカーの慣習に優先する。
出典はすべて sakuri（作者兼プロデューサー）の決定。本書と衝突する実装を
独断で進めてはならない。迷ったら変更せず、論点として報告すること。

---

## 1. 存在形態 — ゲーム画面ではなく、デスクトップの同居者

- 本作は Windows デスクトップ常駐ゲームである。納品形態はデスクトップ版のみ。
  ブラウザ版は作らない（ブラウザで開いても動くこと、を設計目標にしてはならない）。
- 正本の姿は、画面最下部の全幅・透明な帯。キャラクターと家具は壁紙の上に
  直接立つ。部屋・壁・床・窓枠といった「室内の描画」は禁止。家具による
  空間演出は可。
- **中立状態の原則**：メニューを閉じた帯だけの状態がニュートラルであり、
  その状態で体験が完結しなければならない。音・現在のプロジェクト進捗・
  会社の状態は、帯から一目で読めること。管理メニューは取り外し式の
  コンソールであり、開かなければ遊べない機能を作ってはならない。
- 帯の何もない領域はデスクトップへクリックを素通しする（動的ヒットゾーン）。
  デスクトップのアイコン操作を帯が奪う実装は、利便性の欠陥として扱う。

## 2. 時間とプレイヤー連動

- 世界が進むのはプレイヤーの PC が起動している間だけ。電源 OFF は
  「みゅけが眠る」ことであり、進捗は止まる。オフライン進行でこれを
  補ってはならない。
- プレイヤーの現実の作業（タイピング量・カーソル移動距離）はブーストとして
  世界に還元される。ここには厳格なプライバシー契約が伴う：
  - 数えるのはイベントの回数と移動距離だけ。入力内容・キー種別・使用中
    アプリは決して読まない、保存しない。
  - 同意はデフォルト OFF。OFF の間は計測スレッド自体を起動しない。
  - 完全にオフラインで処理する。
  - 絵を描く作業（ペイントソフトでのストローク）も、タイピングと同等に
    「労働」として数える。労働の定義はアプリではなく身体の動きで決まる。

## 3. ゲームプレイ・グラデーション

ゲーム全体の弧は、意図的に設計された勾配である：

- **序盤＝クリッカー**：プレイヤーの手作業がエンジン。
- **中盤＝自動化**：不労所得が増え、手作業の比重が下がる。
- **終盤＝経営手腕**：配分・倍率・売却タイミングの判断が腕の見せ所。

社格ラダーと対応する（インディー/零細＝クリッカー期、中小/中堅＝自動化期、
準大手/大企業＝経営期）。

**最重要の補正 — 「プレイヤーの労働には対価が必要」**：
勾配が規定するのは労働の「比重とてこ」であり、対価の有無ではない。
どのフェーズでも、クリック・実作業ブーストは確実に進行を速めなければ
ならない。「終盤はクリックが効かない」も「終盤もクリック速度が全てを
代替する」も、どちらも理念違反である。

## 4. 成長とインフレ

- バランスの基本方針は2つ：**(1) インフレを恐れない、(2) 成長をはっきり
  体感させる**。数値の膨張は欠陥ではなく設計である。
- 成長の手応えは「解放ジャンプ」（新しい乗数軸の出現）で作る。長い平坦な
  停滞（新しい軸なしに日数だけが過ぎる状態）は構造的な欠陥として扱い、
  停滞区間には新しい倍率の軸を差し込むことで解消する。
- すべての通貨・資源には出口（シンク）を用意する。倍率の積み上げは
  意図的に行い、積み上げ天井を把握したうえで設計する。

## 5. 組織の理念 — 規模は頭数ではなく組織で育つ

- 会社の階梯は6段：インディー → 零細 → 中小 → 中堅 → 準大手 → 大企業。
- 規模は組織の形で表現される：中盤で**部署**（役割の束＋部署レベル＋部長）、
  終盤で**子会社**（半自律の収益単位、配分率の配分が経営判断になる）、
  最終形として**ホールディングス化**（上位通貨・恒常技術への転換）。
- 総勢（自社＋子会社の人数）は帯の上で成長として読めなければならない。
  数字だけ増えて姿が変わらないのは理念違反。

## 6. 依頼の理念 — 仕事は拾うものではなく、組織が取ってくる

- 依頼の手動受注は序盤（クリッカー期）の作法である。組織が育てば、
  営業担当が自動で依頼を獲得するのが正しい姿になる。
- 依頼の**質は担当した営業個人で決まる**（レベル・専門ジャンル・部署の
  育ち具合）。「誰が取ってきたか」は帯とメモで見えること。
  すなわち、スタッフの雇用と育成そのものが経営判断である。

## 7. 周回と永続 — 終わりは「事業売却」

- プレステージの主題は**事業売却（EXIT）**である。「引っ越し」と呼んでは
  ならない（表示文言の話であり、内部キー名は対象外）。
- 売却で会社ランクはリセットされるが、**最高到達社格は永続記録**として
  残る。役員猫・チャレンジ報酬・一部の実績も転換を越えて残る
  —— 周回は「喪失」ではなく「功績を残しての再出発」として設計する。
- 部分売却（子会社単独の売却など）の価値は、全体売却時の寄与と一致する
  よう構成する（カウンター条件）。割に合う/合わない売却経路を混在させない。
- ブランドは品質の複利で育ち、EXIT でリセットされる。技術的負債は
  「急ぐことの価格」であり、デスマーチ出荷（未完でも出荷し負債で払う）と
  有償のバグ外注（高額で負債ごと肩代わり）は、その価格を可視化する
  ための仕掛けである。

## 8. 表現と情報設計

- **鉄則：ビジュアルで説明できることは、文字ではなくビジュアルで。**
  状態（誰が・何を・どれだけ進んだか）は帯の絵で読めることが理想であり、
  テキストは補完に回る。
- 情報の配置は使用頻度で決める。高頻度のものは目立たせ、低頻度のものは
  まとめて格納する。密度を上げても煩雑にしてはならない。
- 機能は抽象的なボタンの列ではなく、帯の上の「モノ」（看板・メモ・電話・
  工具箱など）に宿らせることを優先する。メニューと対応するモノは、
  装飾家具と同じく個別に動かせなければならない。

## 9. 実装の不変条件

- **セーブ互換性**：既存プレイヤーのセーブは常に読み込めなければならない。
  形式変更は加算的に行い、移行処理と「空の状態で既存セーブを上書きしない」
  ガードを必須とする。セーブ保存先の同一性（バンドル識別子）を変えない。
- **数値は sim で証明する**：バランス変更は、本物のゲームコードを偽時計で
  回すバランス計測（tools/game-sim.js）の実測を添える。現行ゲート（改訂3・
  2026-10-27）：初リリース両プロファイル ≤5分、秒5クリックで星屑20個に
  15〜25分、放置だけで星屑20個に3時間以内、同じ買い方なら張り付きのほうが
  速い（星屑比 >1.0。比の目標値は持たない）、5つの経営方針それぞれに最良に
  なる遊び方がある、新しい軸も節目もない区間が張り付き5分・放置30分以内、
  7日目以降の0リリース日 = 0、数値の最大値 < 1e250。体感の主張だけで
  数値を動かさない。
- **報告は帯ファースト**：進捗・検証の提示は帯のスクリーンショットを
  先頭にする。帯こそがゲーム画面であり、管理ウィンドウの撮影は補足である。
- **アートの作者性**：キャラクターの正本は sakuri の手描き。環境アートは
  Codex の一次案を sakuri が手直しする。AI がコードやスクリプトで
  ゲームアートを「生成」することは禁止（変換・組み込み・検証のみ可）。

## 10. 禁止事項（理念違反の早見表）

- ブラウザ版・ブラウザ互換を理由にした設計の歪み
- 部屋・窓枠・カード枠で帯を囲う表現
- 帯がデスクトップのクリックを全面的に奪う実装
- オフライン進行による不在時の補填
- 入力内容・キー種別・使用中アプリの読み取り
- 終盤に労働の対価をゼロにすること（逆に、終盤まで労働が全てを代替することも）
- 「引っ越し」という語でのプレステージ表現
- 既存セーブを壊す形式変更、移行処理なしの保存先変更
- sim の実測なしのバランス変更
- スクリプト生成アートの混入
