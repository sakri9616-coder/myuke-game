# VISIBLE PRODUCTION DESIGN — 帯に「生産が見える」満足感（ジュース）を設計する

目的: オーナー指摘（2026-10-25）「視覚的満足感の演出が足りてない。クッキークリッカーならクッキーがポコポコ湧き、工場シムなら物資がラインに運ばれて、自分の環境の確認と、わちゃわちゃインフレしたときの嬉しさがある」への構造的な答え。
現行の帯は、リリース（紙吹雪＋セレブレート）とリリース時の運搬1回だけが「出来事」で、日常の生産（DP の蓄積・QA・梱包・コイン）は全部不可視。本書は (1) 実システムに正直な「物の流れ」モデル、(2) イベントごとのフィードバック、(3) 生産レートに連動する密度のエスカレーション、(4) 既存部品の再利用を前提にした描画計画と実装フェーズを定義する。

不変条件:
- 帯の正本（STRIP_CANON R1–R14）に適合する: 単一ベースライン R2、描画順 R3（運搬物・一時オブジェクトは④層 = 家具より手前・キャラより後ろ）、高さ予算 R5（上部約30単位の吹き出し域に恒常物を置かない。一時オブジェクトの通過は可）、密度予算 R8（歩行キャラ ≤6、空白 ≥35%）、R10（帯に常時の数値・横断バー・カード状 UI を増やさない。ダイエジェティック表現と一時フロートは Tiny Pasture の頭上ゲージ前例の範囲で可）、R12（クリックは見えている物だけ）、R14（邪魔しない逃げ道を壊さない — 後述の「静かさ」連動）。
- OFFICE_ART_DIRECTION と合成する: カンバンボード（付箋が列を進む）、サーバラック LED（0.55W、CI 所持時）、第2モニタの CI パイプライン表示、モニタのシンタックスコード。本書の流れはその「静止画の文法」の上に「動き」を供給する。
- 数値の正直さ: 流れる物の量は実測の工程スループット・仕掛品（WIP）と対応させる。存在しないコインや進捗を演出で作らない（特にコインは実際に付与されるリリース時にだけ金色のフィードバックを出す）。
- 性能: 60fps・軽量予算。既存パーティクル群（フローター上限12・キラキラ上限10・紙吹雪上限80）の「プール＋上限＋寿命」様式を厳密に踏襲し、フレームごとの新規アロケーションをしない。

現行システムの実測（game/index.html、設計の土台）:
- 生産 tick（1秒）: `produceDP` が `S.wip.code` に入れる（みゅけのコーディング 基本 8 DP/分 ×倍率群、子ねこボット、プログラマ猫。序盤は firstBoost ×3.4）。バグは 0.012/DP で `S.bugStock` に混入。
- 工程: `processPipe(wip, caps, bugF, creditFn)` が毎秒 code → tested → built → shipped を流す。レートは テスト = 30 + 6·自動テスト機 + テスターDP（バグ係数で減衰）、ビルド = 30 + 5·CI + 4·梱包機、出荷 = 30 + 6·ボット + 運搬係DP（いずれも DP/分）。第2ラインは第1ラインの残り容量を共有。
- 仕掛品: `S.wip = {code, tested, built}`（ライン別）。飽和の目安は `stageStatus()` の容量定義（cap = max(60, 下流レート×2分)）で既に存在し、メニューのレート帯（信号機＋仕掛品バー）が使っている。**帯の「山」も同じ frac を使えば、メニューのバーと帯の山が常に同じ事実を指す。**
- 既存の節目: feat 完成（しきい値 = totalDP/(feats+1) ごと、`say` + `pulseMilestone`）、コミット（出荷 100 DP ごと = `BAL.commitEvery`、`doCommit` が音 `phaseComplete` とパルス）、パッケージ数 `S.packages = floor(projectDP/(totalDP/6))`（0–6、現在は帯で不可視）、リリース（コイン・RP 付与、棚に箱、紙吹雪36枚、セレブレート、最寄りスタッフが `carrying` で右端へ 30 単位/秒 → 「+🪙」フローター、`icon_box` を抱える描画あり）。
- スタッフ帯挙動: 徘徊 5–9 単位/秒（役職の持ち場なし、研究員のみ 0.47W ±46 にクランプ）、雑談、訪問猫。運搬は現在リリース時のみ発生し、日常の出荷フローには接続していない。
- 既存のクリックイベント層: 金の魚（10秒、泳ぐ、クリックで 🐟）、バグの群れ（20秒、這う、クリックで各 +6🪙、全滅でボーナス）。本書の流れはこれとは別レイヤー（§4.4 で関係を定義）。

## 1. フローモデル — 帯の上で「何が・どこから・どこへ」流れるか

### 1.1 地理（ゾーンは現行踏襲、流れは左→右の一方向）

帯の読み順は既に「成果は左（棚 0.12W）、仕事は中央、拡張は右」になっている。生産フローはこれに沿わせ、**完成作は左の棚へ、日常の出荷物は右の外へ**という方向の意味論を固定する（現行の運搬＝右端へ、みゅけの棚配達＝左、と既に一致）。

| 地点 | 位置 | 役割 | 対応する実データ |
|---|---|---|---|
| A 発生点: 主机 | 0.30W | コードカードが生まれる場所（みゅけ/ボット/プログラマ猫の生産は全て `wip.code` に合流するので発生点は机で正直） | `produceDP` の蓄積 |
| B QA トレイ | 約 0.40W（机クラスタ右端と研究机の間の空き） | テスト待ち・テスト中の物の「山」置き場。小さな床置きトレイ家具1点 | `wip.code`（テスト待ち）+ テスト処理中 |
| C ビルド置き場 | 約 0.53W（サーバラック 0.55W の足元、未設置時は小さな木箱台） | ビルド待ちの山。サーバ LED の点滅速度がビルドレートに同期 | `wip.tested` |
| D 出荷スタック | 約 0.80W（トロフィー台 0.75W と HUD 域 0.86W の間） | 梱包済み荷物（`icon_box`）の積み場。運搬係がここから右端へ運ぶ | `wip.built` + 出荷済み未運搬分 |
| E 研究机 | 0.47W | 研究Pのモート（微粒子）が生まれる場所（§2） | `S.rp` の整数部の増加 |
| F 第2机 | 0.63W | 第2ラインは自己完結のミニフロー（机の上に小さい山2つまで） | `S.line2.wip` |
| G カンバンボード | 主机の上空 y4–34 | feat 付箋の行き先（§2 の目玉ビート） | feat 完成イベント |
| 左端: 作品棚 | 0.12W | リリース作の配達先（既存のみゅけ配達トリップ） | リリース |

物の流れ: **A で生まれ → B の山でテストを待ち → C の山でビルドを待ち → D で箱になり → 運搬で右端の外へ**。工程間の移動は「次の物の番になった1個」が小さく跳ねて/滑って隣の山へ移る（ベルトは敷かない — R1 の地面文法と R9 に反するため、物の移動は「点の移動」で表現する。Factorio の教訓は「ベルトそのもの」ではなく「滞留が目に見えること」で取り込む）。

### 1.2 量の対応（正直さの規則）

- **山の高さ = `stageStatus()` の frac そのもの**: 各バッファの表示個数 = `round(frac × 表示枠)`（表示枠は B/C とも横2列×最大4段 = 8個、D は箱 最大5個）。frac は「下流が約2分で捌ける量」を満杯とする既存定義なので、メニューの仕掛品バーが満杯になる瞬間に帯の山も天井に届く。山が天井＋赤ランプ色になったら、それがボトルネックの姿（§1.3）。
- **流れる物の発生 = `processPipe` の実績値で駆動**: 毎秒の戻り値 `{test, build, ship}` を量子（初期値 5 DP、§3 でレート連動）に積算し、量子を超えたら対応する移動アニメ（B→C、C→D、D→箱化）を1個発火する。生産側も同様に `wip.code` の増加分から A→B の移動を発火。**アニメの総量は常に実フローの積分と一致する**（端数はアキュムレータに残る）。tick が 1Hz なので発火も最大で秒間数個に自然に収まる。
- パッケージ節目: `S.packages` が増えた瞬間、D の出荷スタックに「完成箱」が1つ光って積まれる（6 分割の進捗が物になる）。これは projectDP 由来の実イベントであり、出荷フローとは独立に数える。
- リリース時: D の残り箱と両ラインの山は一掃され（実際に wip はプロジェクトと共にリセットされる）、コインの噴水（§2）＋紙吹雪（既存）＋棚配達（既存）が同時に起きる。「溜まった物が全部はける」カタルシスをこの瞬間に集約する。

### 1.3 山 = ボトルネック表示（ボードの ⚠ との役割分担）

既存の役割分担（ボードの ⚠ が「一目で読める詰まり」、HUD チップが「どの工程か」の文面）を維持し、山は第三の担当として **「どこに・どれだけ溜まっているか」の量感** を担う:
- テストが詰まる（バグ在庫 > 8 で bugFactor 低下）→ B の山に小さなバグアイコンが湧く（表示は min(8, bugStock) 個まで）。山がバグで覆われたら誰でも「QA が詰まってる」と読める。テスターの QA 処理とみゅけの debug でバグが減るたびにアイコンが1つずつ潰れる（既存のバグ叩きセリフと同期）。
- レート不足の詰まり → 詰まっている工程の**手前**の山だけが伸び続け、下流の山は空になる（飢え）。「山の偏り」がそのまま診断になる。赤変条件は `stageStatus()` の lamp が red の工程に対応する山（判定を二重実装しない）。
- 山をクリック → 工場タブを開いて対策を光らせる（既存 `gotoBottleneckFix()` の導線を流用、§4.4）。

### 1.4 動いていない時（アンビエントとの境界）

- 生産が止まっている状態（企画中・昼寝・集中切れ）ではフローも正直に止まる。代わりに机のモニタに「💡 アイデアのモート」がたまに浮かんでボードの BACKLOG 側へ吸われる（企画中 = ideas が貯まる過程の可視化。発生は ideas の増加イベントから）。
- 猫側のアンビエント（徘徊・雑談・座り・訪問猫）は従来どおり飾りの層として独立に残す。生産の物は猫の歩行を邪魔しない（描画は④層で猫より後ろ、当たり判定なし — R12 の例外ではなく「物はクリック対象にしない」が原則。例外は §1.3 の山クリックのみ）。

## 2. フィードバック・ビート — イベントごとの見せ方

凡例: 「大きさ」は量へのスケーリング。音は既存 SoundKit の節目音に相乗りし、新規の常時音は足さない（帯は音 OFF 既定の静けさが正本 R14）。

| # | イベント（実フック） | 見せ方 | 大きさのスケーリング | 区分 |
|---|---|---|---|---|
| 1 | コード生成（`wip.code` 増加の積算） | 机のモニタ前に小さな**コードカード**（白い小カードにシンタックス色の短線2–3本、OFFICE §2.2 の画面文法と同色）がポンッと生まれ、B の山へ小さく跳んで落ちる。発生時に既存キラキラプールから星1–2個 | 量子 5 DP に1枚（§3 で調整）。クリック応援の +DP フローターとは別物（あちらは「あなたの入力」、こちらは「会社の生産」） | 生産 |
| 2 | テスト通過（pipe.test の積算） | B の山の最上段のカードが**緑の✓印**を一瞬付けて C へ移動。テスター在籍時はテスターの頭上に小さな ✓ がポップ | 量子ごと1枚。バグ係数で実効レートが落ちれば移動も正直に遅くなる | 生産 |
| 3 | バグ発生・滞留（bugStock 増加/減少） | B の山にバグアイコン（既存 `icon_bug` 流用）が這い出す/潰れる。debug 中はみゅけの既存バグ叩きアニメと同期して1匹ずつ弾ける | 表示 min(8, bugStock)。8 超で山の縁が赤く滲む | 生産 |
| 4 | ビルド完了（pipe.build の積算） | C の山の物が**箱（`icon_box`）に姿を変えて** D へ。サーバ設置時は LED が一瞬速く点滅（ビルドの鼓動） | 量子ごと1個 | 生産 |
| 5 | 出荷（pipe.ship の積算） | D の箱を運搬係（いなければボット/最寄りスタッフ）が右端まで運び、画面外で小さく **「+DP」ではなく箱が消える＋極小の✦**。日常の出荷ではコインを出さない（正直さ §不変条件）。代わりにボードの % が伸びるのが報酬 | 運搬は実フローに追従するが、見た目の同時運搬は最大2個まで（§3） | 生産 |
| 6 | コミット（出荷 100 DP ごと、既存 `doCommit`） | 第2モニタ（ターミナル/git ログ面）に**新しいログ行が1行スクロールイン**＋机の上に小さな「コミットカード」が一瞬立つ。既存の `pulseMilestone` と音はそのまま | 固定（節目） | 節目 |
| 7 | feat 完成（既存しきい値イベント） | **付箋が机からボードへ飛び、DONE 列に貼り付く**（放物線 0.6 秒、到着でボードが小さく揺れる＋付箋が金色に一瞬光る）。OFFICE §2.1 のカンバン文法の「動き」担当。`say` の完成セリフと同時 | 固定（節目）。これが中盤以降の最も嬉しい定期ビートになる | 節目 |
| 8 | パッケージ節目（`S.packages` 増加） | D スタックに完成箱が光って積まれる＋小さな「📦」フローター（既存フローター流用） | プロジェクトあたり最大6回 | 節目 |
| 9 | 研究P（`S.rp` 整数部の増加） | 研究机から **🔬色のモート**（紫 = RP の意味色、C586C0 系）が1つ浮かんで消える。研究員不在時は発生なし | RP +1 ごと（端数は実データ側に蓄積済み） | 生産 |
| 10 | リリース（既存イベント群） | 既存（紙吹雪・セレブレート・棚配達・棚グロー）に **コインの噴水** を追加: 棚の新箱から `icon_coin` が放物線で湧き、右下 HUD 方向へ吸い込まれて消える（Cookie Clicker の「落ちてくるクッキー」の帯版 = 報酬が画面を横切る） | 個数 = clamp(6 + coins/40, 6, 28)。金額が大きいほど湧く | 節目 |
| 11 | クリック応援（既存） | 既存のキラキラ＋「+n DP」フローター＋CRITICAL を維持。生産フロー（#1）と混ざらないよう、応援のカードは発生させない（入力の手応えはフローターが担当済み） | 既存どおり | 入力 |
| 12 | 差し入れ・お世話（既存 careTimer） | 差し入れ係が机まで小走りで来て 🍵 フローター（現行はログ＋セリフのみ）。任意・低優先（§5 の P4） | 固定 | アンビエント寄り |

「ポコポコ感」の中核は #1–#5 の連鎖で、単発の派手さではなく **「生まれて→流れて→溜まって→はける」の因果が常時見える** こと。#7 と #10 が定期・大型の山場を担当する。

## 3. エスカレーション — 生産レートで景色の密度が育つ

### 3.1 ティア定義（判定は総スループット T = productionRate + line2Rate、DP/分。10秒ごとに再判定し、上下動でちらつかせないため降格は30秒遅延）

| ティア | T の目安 | 景色 | 対応する会社の姿 |
|---|---|---|---|
| T0 静か | < 15（序盤・企画中・就寝帯） | フローは点滴: カードは数十秒に1枚。山はほぼ平ら。アンビエント（猫の徘徊・雑談）が主役 | 創業期〜企画中 |
| T1 稼働 | 15–60 | カードが数秒に1枚流れ、山が1–3段で呼吸する。運搬が時々歩く | 初リリース〜スタッフ1–2人 |
| T2 活況 | 60–150 | カードの流れがほぼ連続。山が育ってははけるリズムが見える。運搬は往復が途切れない。コミットのログ行が定期的に流れる | ライン成熟・第2ライン稼働 |
| T3 わちゃわちゃ | ≥ 150 | 「嬉しい混雑」: カードは**束表示**（1枚に「×3」相当の厚み）で流れ、箱が積み上がり、運搬2名体制、feat 付箋とコインの小噴水が重なる。ただし上限で頭打ち（§3.2） | 終盤・転生後の加速帯 |

- 量子 q（1枚のカードが表す DP）はティアで切り替える: T0/T1 は 5 DP、T2 は 10 DP、T3 は 20 DP。**見た目の流量（枚/分）がティアを跨いでも 2 倍程度しか増えない** ようにし、インフレは「枚数」ではなく「束の厚み・山の育ち・同時に動く人数」で表現する（Cookie Clicker が数字の桁でインフレを見せるのと同じ発想を、帯では“密度の質”に翻訳）。
- ティアは OFFICE のオフィス規模ティア（家具の素材・サーバ有無）と直交する軸だが、視覚的には連動して見える（規模が上がれば生産も上がるのが通常）。判定を共有する必要はない。
- 降格（夜間・放置で生産が落ちる）は景色が静かに戻ること自体が「おやすみ」の合図になる。R14 の集中/静音系設定とは別に、帯の「かくす」中は当然すべて止まる。

### 3.2 上限とプーリング（fps を落とさない・猫を覆わない）

- **同時表示上限（ハードキャップ）**: 移動中の物 ≤ 10 個、山の表示 ≤ B8 + C8 + D5 + F（第2ライン）各4、バグ表示 ≤ 8、モート類 ≤ 6、コイン噴水 ≤ 28（寿命 0.9 秒の使い捨て）。フローター12・キラキラ10・紙吹雪80 の既存プールとは別枠だが、**全パーティクル合計 ≤ 140** を全体キャップとし、超過時は古い装飾系（モート→キラキラ→フローターの順）から間引く。実データ連動の山・移動物は間引き対象にしない（正直さ優先、装飾を先に落とす）。
- 実装は既存の作法どおり: 固定長配列＋ `born` 時刻＋寿命フィルタ（`stripConfetti` / `stripFloaters` と同型）。移動物の更新は `stripUpdate(dt)` 内、描画は R3 の④層で `sR` / `sDrawSprite` のみ。新規の画像アセットは作らない（カード・箱・バグ・コインは既存スプライトと手続き描画で足りる）。
- 極端なレート（転生直後の加速・ブースト集中）では: 量子が最大でも追いつかない場合はアキュムレータ側で「束ね係数」を上げる（1枚 = q×2, ×4… と可変にし、カードに小さな束ねバッジを描く）。**アニメ本数を増やすのではなく1個の意味量を増やす**のが原則で、これにより T が 10 倍になっても描画本数は一定に保てる。
- 山が上限に達した後の WIP 増加は「山の色が深くなる＋縁の赤滲み」で表す（個数を増やさない）。frac が 1.0 を超える分は色で正直に示す。
- 運搬の同時数は最大2。D に箱が残っていても運搬係が足りなければ積み残しとして見える（それ自体が出荷ボトルネックの正直な姿）。

### 3.3 猫を守る規則

- 物の移動経路は地面ライン上（y は接地線付近のみ、猫の頭上を横切らない）。吹き出し域（上部）に入るのは feat 付箋の飛行（0.6 秒の一時通過）とコイン噴水の放物線頂点だけ。
- 物は猫と重なってよいが（④層 = 猫の後ろ）、猫の顔・吹き出しを覆う配置にはしない。山の設置場所は猫の待機位置（机・研究机の前面）と重ならない脇位置に固定する。

## 4. 描画計画 — 既存部品の再利用と新規部品

### 4.1 そのまま再利用するもの

- パーティクル基盤: `addStripFloater`（上限12・1.4秒）、`stripSparks`（上限10・0.4秒）、`spawnStripConfetti`（上限80・2.2秒）とその描画・寿命フィルタの型。

- 節目パルス: `pulseMilestone()` / `milestonePulseUntil`、棚グロー `shelfGlowFrame`、`say()`。
- 判定: `stageStatus()` の frac・lamp（山の量と色）、`currentBottleneck()`（山クリックの遷移先）、`processPipe` の戻り値（フロー駆動）。
- スプライト: `icon_box` / `icon_bug` / `icon_coin` / `icon_idea`（いずれも 16×16 で定義済み）。

### 4.2 新規に要るもの（すべて手続き描画 or 既存スプライトで、新規アセット制作なし）

1. **フロープール** `stripFlow = []`（上限 10）: `{kind:"card"|"box"|"note"|"coin"|"mote", from, to, t, dur, arc, stack}`。更新は `stripUpdate`、描画は④層。カードは `sR` の白矩形＋シンタックス色の短線2–3本（モニタ画面と同色セットで描く関数を共有化）。
2. **山レンダラ** `drawStripPiles()`: B/C/D/F の各置き場に、frac から決まる個数のカード/箱を「横2列×段」の格子に描く小さな関数。置き場の床には薄いトレイ/台（高さ 3–4 単位の家具小物として R9 の範囲）。バグ滞留時は最上段に `icon_bug` を重ねる。
3. **フローアキュムレータ**: tick 側に `{code:0, test:0, build:0, ship:0}` の端数保持と、量子発火の小さな関数群。`processPipe` の戻り値と `wip.code` の差分を毎秒受け取るだけの薄い層（ゲームロジックには触らない — 読み取りと演出のみ）。
4. **付箋フライト**: feat 完成フック（`creditProject` の feat ループ内、既存 `say` の隣）から `stripFlow` に note を1枚投入し、到着時にボード側の付箋表示を1つ進める。ボード描画（OFFICE P3 のカンバン化）と協調: ボード未改修の段階では「ボード枠の金パルス」（既存）にフォールバック。
5. **コイン噴水プール** `stripCoins = []`（上限 28）: リリース時に棚の新箱位置から湧き、放物線＋右下方向への吸着で消える。`icon_coin` の `sDrawSprite` のみ。
6. **git ログ行**: 第2モニタの描画（OFFICE §2.2）に、コミット時に1行追加されるログバッファ（最大4行の文字列配列、描画は小さな色行で代替可 — 文字を描く場合は既存のモニタ内描画の流儀に合わせる）。

### 4.3 置き場の家具（最小限の追加）

- B: 床置きトレイ（幅 ~26、高さ 3）／ C: 木箱台（サーバ未設置時）／ D: 出荷口の小さな台＋「出荷」札（高さ ≤ 20、R5/R9 内）。いずれも既存 E スロット外の「工程置き場」として机クラスタと第2机の間の歩行レーン脇に置くが、R8 の密度予算と衝突しないよう、**主要家具には数えない小物級**（フットプリント合計は帯幅の 45% 制限に収まることを §5 の検証で確認）。置き場は固定比率位置とし、幅が変わっても工程の順序（左→右）が崩れないことを優先する。

### 4.4 クリック・ヒットゾーンとの関係（既存イベントと重複させない）

- 既存の金の魚・バグの群れは「プレイヤーの能動イベント」として存続。本書のフロー物は**クリック対象にしない**（R12 は「見えている物に当たりがある」原則だが、常時流れる物を対象にすると誤クリックで猫の操作を奪う。魚・バグは一時的で大きく、フロー物は常時で小さい — 役割が違う）。
- 唯一の例外: **赤く詰まった山** は `stripHitRects` に登録し、クリックで `gotoBottleneckFix()` 相当（工場タブ＋対策ハイライト）へ飛ばす。これは「問題のある場所を触ると直し方が開く」発見可能性のための導線で、通常の山は素通り（デスクトップへのクリック通過を維持）。
- HUD・棚・ボードの既存ヒットゾーンには触らない。

## 5. 実装フェーズ（満足度 ÷ 労力 順）と検証

### Phase 1 — 山とパッケージ（静止画の正直さ）★最初の山場
- `drawStripPiles()`（B/C/D/F）＋ `stageStatus` frac 連携、バグ滞留のバグアイコン、`S.packages` 増加時の完成箱＋フローター、詰まった山のクリック導線。
- 労力小（新規は山レンダラと置き場だけ）で、「生産が見える」体感の 6 割はここで得られる（Cookie Clicker の「クッキーが積み上がる」＝在庫の可視化が本質のため）。
- 検証: レート注入セーブ（後述）で山の frac とメニュー仕掛品バーの一致を目視＋スモークで `stageStatus` と表示個数の対応を assert。

### Phase 2 — 流れと付箋（動きの因果）
- フローアキュムレータ＋ `stripFlow`（カードの A→B→C→D 移動、箱化、出荷運搬の日常化 = carrying 発火条件の拡張）、feat 付箋フライト（ボード金パルスへの着地から）、コミットの git ログ行、研究モート。
- 検証: 注入レートを変えて移動アニメの総量が `processPipe` 積分と量子誤差内で一致すること（アキュムレータの残量を含めて assert 可能）。

### Phase 3 — リリースの噴水とエスカレーション
- コイン噴水（金額スケーリング）、ティア判定と量子切替・束ね表示、全体パーティクルキャップと装飾の間引き順序。
- 検証: T0–T3 の4段階の注入セーブでスクリーンショット（1280幅・帯ファースト）を取り、密度・空白率（R8: 家具＋物でも視覚的な空白が残ること）・猫の可読性を目視確認。fps は実バイナリ＋Xvfb で render ループのフレーム時間を計測し、T3 でも 16ms 枠に収まることを確認（既存の two-window-test と同系の計測）。

### Phase 4 — 仕上げ（任意・低優先）
- 差し入れの配達アニメ（#12）、第2ラインのミニフローの精緻化、サーバ LED とビルドレートの同期点滅、子ねこボット専用の小型運搬（ボットが D まで箱を押していく等）。

### 検証基盤（全フェーズ共通）
- **レート注入**: 検証用にセーブを段階別に用意する（新規 / 初リリース後 / スタッフ3人＋ライン成熟 / 第2ライン＋転生加速）。既存の `tools/balance-sim.js` の到達点と `tools/strip-fresh-measure.js` の実測作法を流用し、「T（DP/分）→ ティア → 表示個数」の対応表を実測で埋めてから定数を固定する。
- スモーク追加: (a) frac→表示個数の単調性と上限、(b) アキュムレータの保存則（発火量＋残量 = 実フロー積分 ± 量子）、(c) パーティクル総量キャップ、(d) 山クリックのヒットゾーンが赤状態でのみ存在すること。
- 帯ファーストの報告作法どおり、スクリーンショットは帯 → 帯ズーム → （必要な場合のみ）パネルの順。
