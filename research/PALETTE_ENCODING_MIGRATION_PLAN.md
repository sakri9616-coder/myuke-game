## 2. 枯渇時に何が起きるか（現行の安全側の挙動）

- `import-sakuri-art.py` の `frames_to_rows()` は、プールに空きがなければ
  `ValueError("palette char pool exhausted")` を出して中断する。
- 書き込み（`sprites.js`・`game/index.html` 埋め込みコピー）はその後段なので、
  **枯渇しても既存ファイルは壊れない**（中途半端な書き込みは起きない）。
  ただしそのバッチの統合は止まる。ここが「バッチ途中で強制移行」になる理由で、
  計画だけでも先に決めておく価値がある。

## 3. 守らなければならない不変条件（ここを外す案は不採用）

行文字列はダブルクォートの JS 文字列リテラルに **エスケープなし** で書き出され
（`entry_text()` の `"%s"`）、描画側は `pal[row[x]]` で 1 単位ずつ引く
（`game/index.html` のスプライトキャッシュ生成部）。
Python 側の行幅検査も `len(row)`（コードポイント数）で行う。
よってプール文字は次をすべて満たすこと：

1. **BMP のみ**（U+0000〜U+FFFF、サロゲート U+D800〜U+DFFF を除く）。
   圏外文字（絵文字など）は JS で 2 単位・Python で 1 文字になり、
   幅とピクセル対応が崩れる。絶対に使わない。
2. **透過マーカー `.` との衝突なし**。`.` は予約済み。
3. **JS 文字列リテラルを壊さない**：`"` と `\` は使わない。
   行終端文字 U+2028／U+2029（JS の行終端子）も使わない。
4. **結合文字・異体字セレクタを使わない**（表示・編集時に隣と一体化する恐れ）。
   繰り返し記号（`ゝゞヽヾ`）や中点 `・`（`.` と見間違える）も避ける。
5. **既存パレット・既存プールとの重複なし**。
6. **sakuri の原画との完全一致は維持する**（後述の量子化案の不採用理由）。

## 4. 採用する移行方針：プールの BMP 拡張（Tier 方式）

**形式を変えない。** `CHAR_POOL` の末尾に新しい文字ブロックを追加するだけ。
既存の割当はプールの先頭側に固定されているため、末尾追加は既存割当に
一切影響しない（前方互換・接頭辞安定）。

### Tier 1（次に使う 176 文字・本計画で確定）

- ひらがな 86 文字（U+3041〜U+3096）：
  `ぁあぃいぅうぇえぉおかがきぎくぐけげこごさざしじすずせぜそぞただちぢっつづてでとどなにぬねのはばぱひびぴふぶぷへべぺほぼぽまみむめもゃやゅゆょよらりるれろゎわゐゑをんゔゕゖ`
- カタカナ 90 文字（U+30A1〜U+30FA）：
  `ァアィイゥウェエォオカガキギクグケゲコゴサザシジスズセゼソゾタダチヂッツヅテデトドナニヌネノハバパヒビピフブプヘベペホボポマミムメモャヤュユョヨラリルレロヮワヰヱヲンヴヵヶヷヸヹヺ`
- 検証済み（2026-10-26）：現行パレット・現行プールとの衝突ゼロ、
  全文字 BMP・サロゲートなし・禁止文字（`" \ .`・U+2028／U+2029）なし。
- 選定理由：ラテン文字・数字・記号と見た目が重ならず、行文字列の中で
  既存キーと誤読しにくい。ギリシャ文字・キリル文字はラテン文字との
   homoglyph（Α≒A、А≒A など）が多く、行の目視確認で混同する恐れがあるため
  Tier 1 には採用しない。

### Tier 2（Tier 1 を使い切った場合の予備・文字だけ決めておく）

- CJK 統合漢字（U+4E00〜U+9FFF、約 2 万字）。実質的に枯渇しない。
  Tier 1 と同じ不変条件を満たすことだけを確認して使う。
  Tier 2 の導入時も形式変更は不要（末尾追加のみ）。

## 5. 不採用の案と理由

- **2 文字符号化**：描画側 `row[x]` の単位読解、行幅（`rows[0].length`）、
  validator の行検査・パレット正規表現、既存全行の再符号化、
  `game/index.html` 埋め込みコピーの同期まで波及する大改造。
  BMP だけで実質無限に足りる以上、割に合わない。
- **スプライト単位パレット（マップ方式）**：Codex 環境アート
  （`graphics/env-sprites-*.js`）は既にファイル単位パレットだが、
  共有パレット側へ持ち込むと描画側の構造変更になる。Tier 方式で足りる。
- **色量子化（近似色を既存色へ寄せる）**：新規色の伸びは抑えられるが、
  **sakuri の原画と完全一致しなくなる**。sakuri アート統合の条件
  （原画と完全一致）に反するため、共有パレット側では不採用。
  Codex 環境アート側の判断は別途（本計画の対象外）。

## 6. 実装のトリガーと手順（実装する回への申し送り）

### トリガー

次のいずれかを満たしたら、そのバッチの統合前に Tier 1 を実装する：

- (a) 統合予定のアートの新規色数が、残りプール数（現在 8）を超える見込みのとき。
- (b) 残りプール数が 8 を下回ったとき（すなわち次のバッチで枯渇が確実なとき）。
- トリガーに当たらないバッチでは、プールに触らない（不要な変更をしない）。

### 事前チェック（バッチごとに 1 分でできる）

1. 統合対象の `.aseprite`／PNG から新規色数を数える。
   簡易法：既存パレットに無い RGB を `frames_to_rows()` の監査出力
   （`added`）で確認する。コピー上の試し取り込みでもよい。
2. 新規色数 ≤ 残りプール数なら、現行プールのまま統合する。

### 実装手順（Tier 1 導入時）

1. `tools/import-sakuri-art.py` の `CHAR_POOL` の末尾に Tier 1 の 176 文字を
   そのまま追加する（既存の並びは一切並べ替えない。コメントに
   「Tier 1（ひらがな＋カタカナ、2026-10-26 計画）」と由来を書く）。
2. `CHAR_POOL` 追加分の文字が §3 の不変条件を満たすことを、
   スクリプトで機械確認する（BMP・重複なし・禁止文字なし）。
3. そのバッチを通常手順で統合する（原画と完全一致の条件は従来どおり）。
4. validator のパレット総数 assert とバッチ内訳コメントを更新する
   （従来のバッチ作業と同じ手順。総数を書き換えるだけでは済ませず、
   内訳に当該バッチの新規色数を追記する）。
5. 検証：`graphics/validate-sprites.cjs` PASS、
   `tools/verify-all.sh`（smoke＋sim ゲート＋帯スクショ）PASS、
   埋め込みコピー同期（validator が検査）を PASS で確認する。
   さらに、統合した新規スプライトが帯に描画されることを帯スクショで目視する。

### ロールバック

- Tier 1 の文字が 1 つも割り当てられていない状態なら、末尾追加の除去は
  無害（既存割当に影響なし）。
- 割り当て済みの文字をプールから除去してはいけない（その色の行が
  描画できなくなる）。ロールバックは「次のバッチで Tier 1 を使わない」
  ではなく「割り当て済みを残し、未使用の残りだけを除去する」形に限る。
  実務上は、Tier 1 導入後に除去する理由がないため、導入は不可逆として扱う。

## 7. 対象外・注意事項

- 本計画の対象は `graphics/sprites.js` の共有パレット（sakuri アート統合経路）のみ。
  Codex 環境アート（`graphics/env-sprites-*.js`）はファイル単位パレットで、
  `CHAR_POOL` の影響を受けない。
- 本計画は sakuri のアートそのもの・既存スプライト・ゲームの数値・
  セーブ形式には一切触れない。
- 次のバッチで Tier 1 が要るかどうかは、バッチ到着時に §6 の事前チェックで決める。
  計画書の存在自体は、プール残量の監視義務を生まない（バッチ時のチェックで足りる）。
